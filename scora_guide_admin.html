API version 2026-08

Build a Scora app safely

This guide documents the APIs and app surfaces currently implemented in Scora. Use the versioned OAuth GraphQL API for a new external app.

1. Configure the app

Required scopes: permissions a merchant selects at installation.

Optional scopes: permissions requested later and usable only after merchant approval.

Admin API redirect URIs: exact OAuth callback URLs; unlisted URLs are rejected.

Billing plans: recurring plans that start as a merchant-approved pending request.

Extensions: storefront, admin, account, checkout, POS, Flow, data-source, or sandbox surfaces.

Webhooks and proxy: event delivery and storefront proxy configuration, not Admin API authentication.

2. Connect a merchant with OAuth

Run this flow on your backend. Never expose the client secret or PKCE verifier in browser JavaScript.

  1. Create a PKCE verifier, its S256 challenge, and a random state value.
  2. Redirect the merchant to the authorize URL.
  3. Verify state after Scora redirects to the registered callback with a one-time code.
  4. Exchange the code server-side, then call GraphQL with the access token.
GET https://scora.com.pk/api/admin/oauth/authorize?client_id=APP_ID&installation_id=INSTALLATION_ID&redirect_uri=https%3A%2F%2Fapp.example.com%2Foauth%2Fcallback&scope=products%3Aread&state=RANDOM_STATE&code_challenge=PKCE_S256_CHALLENGE&code_challenge_method=S256

POST https://scora.com.pk/api/admin/oauth/token
Content-Type: application/json

{"grant_type":"authorization_code","client_id":APP_ID,"client_secret":"BACKEND_ONLY_SECRET","code":"ONE_TIME_CODE","redirect_uri":"https://app.example.com/oauth/callback","code_verifier":"ORIGINAL_PKCE_VERIFIER"}

Access tokens last 15 minutes. Refresh tokens last 30 days, rotate on use, and a reused refresh token revokes its token family.

3. Call versioned GraphQL

Endpoint: https://scora.com.pk/api/admin/2026-08/graphql.

POST /api/admin/2026-08/graphql
Authorization: Bearer ACCESS_TOKEN
Content-Type: application/json
Idempotency-Key: unique-retry-key

{"query":"query { products(first: 10) { nodes { id title handle price } } }"}

Each token is bound to one active app installation and store. Scopes, request size, query depth, aliases, cost, pagination, rate limits, and mutation audit checks are enforced.

4. Billing and optional permissions

These mutations create a request only. They cannot charge a merchant or grant a permission automatically.

mutation RequestPlan {
  appSubscriptionRequest(input: { planKey: "pro", clientMutationId: "plan-001" }) {
    subscriptionId status message userErrors { message code }
  }
}

mutation RequestPermission {
  appOptionalScopesRequest(input: { scopes: ["orders:read"], clientMutationId: "scope-001" }) {
    scopeRequestId status scopes message userErrors { message code }
  }
}

`appSubscriptionCancel` and `appUsageRecordCreate` are also available. Usage and subscription operations require billing:write; an active subscription is required for usage.

5. Surfaces and integration requirements

Embedded admin links: Scora hosts the authenticated page and sandboxes your configured URL in an iframe. Its short-lived embedded session token is not an Admin API bearer token.

Sandbox functions: Scora runs the JSON expression itself. It cannot make network, database, filesystem, or other I/O calls.

  • Store client secrets, refresh tokens, webhook secrets, and PKCE verifiers on your backend only.
  • Use the versioned OAuth API for new apps. The older /core/app-graphql.php and /core/app-api.php routes exist only for compatibility.
  • Use only merchant-approved scopes and handle userErrors returned by every mutation.

6. Verify a payment callback

A gateway callback is active only after the developer portal verifies it. Use a public HTTPS URL. Localhost, private or metadata IPs, custom ports and redirects are rejected. Changing the URL requires a new verification.

Scora POSTs a random challenge and timestamp, signed in X-Scora-Signature as v1=HMAC-SHA256(timestamp + "." + raw body, app client secret). Validate it on your backend, then return HTTP 2xx JSON containing the exact challenge and timestamp plus signature calculated as v1=HMAC-SHA256(timestamp + "." + challenge, app client secret).

{"type":"scora.gateway_webhook.verify","challenge":"RANDOM_HEX","timestamp":1735689600}
{"challenge":"RANDOM_HEX","timestamp":1735689600,"signature":"v1=RESPONSE_HMAC"}

A verified callback is required before appSubscriptionPaymentConfirm can activate a subscription. This proves control of the endpoint; your backend must still verify the provider's own webhook signature before confirming payment.
